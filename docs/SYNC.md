# Sync & Auth Contract

Backend: Supabase (Postgres + Auth + Realtime). Project URL and publishable key live in
`config/supabase.json` (publishable keys are designed to ship in clients; row-level
security is what protects the data). No secret/service-role key ever goes in this repo.

## Auth

- Email + password via Supabase Auth (GoTrue). Sign up, sign in, sign out, password reset email.
- Sessions: access token (JWT, ~1h) + refresh token. Both apps refresh automatically.
- On first sign-up the database trigger `handle_new_user` creates the `settings` row and
  the 14 default categories. Clients must **not** seed categories themselves.
- Android requires one online sign-in on first launch; afterwards it works fully offline.

## Tables & keys

| Table | Primary key used for upsert (`on_conflict`) |
|---|---|
| settings | `user_id` |
| months | `user_id,year,month` |
| budgets | `user_id,year,month,category_id` |
| net_worth_snapshots | `user_id,taken_on`: **pull-only**. Clients never push it; they call RPC `take_net_worth_snapshot()` instead (DOMAIN_RULES §5b) |
| categories, transactions, recurring_items, accounts, ledger_entries, meal_plans, meal_items | `id` (uuid, generated by the client with UUID v4) |

Clients always send `user_id` (= the signed-in user's id) on writes.

## Rules

1. **Never hard delete.** Deleting = upsert with `deleted: true`. Cascades are done by the
   client (deleting a meal plan tombstones its items; deleting a category is not allowed while
   it has data. Archive instead).
2. **`updated_at` is server-owned.** A trigger sets it to `clock_timestamp()` on every write.
   Clients never send it (or it is ignored).
3. **Pull** per table: `GET /rest/v1/{table}?updated_at=gt.{cursor}&order=updated_at.asc&limit=1000`
   (page until < 1000 rows). Cursor = max `updated_at` seen − 10 seconds overlap. Upserting a
   row twice is harmless. Store a cursor per table.
4. **Push**: the client keeps a dirty flag per local row. Push dirty rows with
   `POST /rest/v1/{table}?on_conflict=...` and header `Prefer: resolution=merge-duplicates,return=representation`.
   Clear the dirty flag only if the row was not edited again while in flight. Write the returned
   row (with server `updated_at`) back locally.
5. **Conflicts**: last write to reach the server wins, per row. Acceptable for a single-user app.
   During pull, a remote row never overwrites a local row that is still dirty. That row is pushed next.
6. **Order**: push, then pull. Push order: settings, categories, months, budgets, accounts,
   recurring_items, ledger_entries, meal_plans, meal_items, transactions (no FKs, so order is
   only cosmetic).
7. **Triggers** (Android): on app start/resume, right after any local edit (debounced ~1.5s),
   on connectivity regained, and a periodic WorkManager job (every 6h, network required).
   Web: realtime subscription to all tables (`postgres_changes`, filter `user_id=eq.{uid}`)
   plus a full refetch on tab focus and on reconnect.
8. Sign-out clears local data on Android only after a successful final push (or after the
   user confirms losing unsynced changes).

**Import = merge**, never wipe:
- Categories are matched to existing ones **by name (case-insensitive)**; when matched, the
  file's category id is remapped to the existing id everywhere in the file (budgets,
  transactions, recurring_items, accounts.linked_category_id). Unmatched categories are inserted.
- Months / budgets upsert by natural key. Everything else upserts by id.
- Settings from the file overwrite current settings.
- `net_worth_snapshots` (optional in the file) upsert by `user_id,taken_on` with `source: "import"`; this is the
  only time a client writes that table directly. After import, call `take_net_worth_snapshot()`.
- Show a preview ("This will add 6 months, 158 transactions …") and require confirmation.
